# A：融合基线 · 实现说明

由 B/C 组整理，供 A 参考。本文中的数字都注明了来源文件。基线结果目前**未完成**，要等 B/C 矩阵中无扰动的 clean 运行跑完，再由脚本汇总填入。

## 1. 研究问题

在正常（easy）序列和困难（hard）序列上，分别加入 IMU 和深度后，定位精度、有效轨迹覆盖率和计算耗时各有什么变化？

A 不单独跑实验。基线数字取自 B/C 矩阵里同种子、同 IMU 噪声的 clean 运行，这样 A 与 B/C 用的是同一批运行，可以直接对照。

## 3. 数据（摘要）

- 数据集：TartanAir V2 Office，轨迹 P004，前向左相机。easy 1220 帧（121.9 s），hard 817 帧（81.6 s），图像 10 Hz、640×640，fx=fy=cx=cy=320。
- 深度：uint16 PNG，单位为米×1000，0 表示无效。IMU 为 100 Hz。原始 IMU 是无噪声的，正式实验用 `imu_noisy_s<seed>.csv`，噪声种子与实验种子一致。
- 来源：`data/seqs/<序列>/convert_info.json`；准备步骤见 `SETUP.md` 第 3 节。

## 4. 运行入口

### 4.1 命令

```bash
# 单次运行
IMU_SEED=0 scripts/run_orbslam.sh IMU_RGBD data/seqs/office_easy_p004 OUT_DIR
# B/C 矩阵中的基线由 run_matrix.py 调用同一入口，基线即 clean 运行
```

### 4.2 运行方式

- **代码**：`scripts/run_orbslam.cc`，编译产物为 `bin/run_orbslam`。只调用 ORB-SLAM3 的公开接口，不修改优化器。
- **模式**：支持 MONOCULAR、IMU_MONOCULAR、RGBD、IMU_RGBD 四种，后文分别简称 RGB、RGB+IMU、RGB-D、RGB-D+IMU。不开 Pangolin 可视化。
- **回放**：`--rate 1` 按 10 Hz 实时回放，处理不过来时也不丢帧。
- **起始时刻**：`--start 0.2`，跳过前 0.2 s，避开 TartanAir IMU 样条的端点效应。所以实际 easy 用 1218 帧，hard 用 815 帧。
- **IMU 输入**：每帧喂入时间戳在 (上一帧, 当前帧] 内的 IMU 样本。`IMU_SEED=s` 表示选用 `imu_noisy_s<s>.csv`。

### 4.3 输出

| 文件 | 内容 |
|---|---|
| `tracking.csv` | 每帧一行：`timestamp,valid,state,quality_rgb,quality_depth,source,latency_ms,map_id,frame_epoch,imu_init` |
| `trajectory_online.tum` | 在线轨迹（主指标）：每个 OK 帧当时输出的 T_w_c |
| `trajectory_est.tum` | 最终轨迹（副指标）：ORB-SLAM3 全局优化后的轨迹，只包含最大地图，且只保留在线 OK 的帧 |
| `frame_events.csv` | 世界系每次重新定义的时刻与原因 |
| `run.log`、`run_info.json` | 运行日志与运行参数 |

`tracking.csv` 各列的含义：

- `valid=1`：当且仅当 `GetTrackingState()==OK`。
- `source`：值为 SLAM、IMU 或 NONE。在 IMU 模式下，RECENTLY_LOST 状态的帧标为 IMU，表示这是 IMU 预测，不算有效帧。
- `quality_rgb`：跟踪到的地图点数。
- `quality_depth`：非零深度像素所占比例。

### 4.4 已知问题

当前地图刚被重置为空时，ORB-SLAM3 的 `SaveTrajectoryEuRoC` 会段错误。现在这一步放在子进程中执行：崩溃时 `trajectory_est.tum` 为空，并记为“无最终轨迹”，**不会记为 0**。这种情况只在 hard 序列的 IMU 模式下出现。

## 5. 评测口径

评测脚本为 `scripts/evaluate.py`。

- **配对**：估计位姿与 GT 按时间戳配对，容差 5 ms。ATE 和 RPE 只在配对成功的有效帧上计算。
- **对齐**：RGB（单目）用 Sim(3)，其余模式用 SE(3)，两者不混用。
- **主指标：在线轨迹 ATE。** 按 (map_id, frame_epoch) 分段，每段单独对齐，总 ATE 按帧数加权。少于 3 个位姿的段不参与对齐。**分段越多，ATE 越乐观，所以段数必须和 ATE 一起报告。**
- **副指标：最终轨迹 ATE。** 对整条最终轨迹做一次全局对齐。
- **RPE**：Δ=1 s，报告平移（m）和旋转（°）。
- **覆盖率**：有效帧数 ÷ 总帧数。
- **失跟事件**：首个有效帧之后出现的连续无效帧，算一次事件。
- **恢复**：连续 3 帧有效，且对齐后误差不超过 0.5 m。未恢复的单独计数，**不填 0**。

## 6. frame_epoch：在线轨迹的世界系分段

**为什么需要分段。** ORB-SLAM3 运行时会多次重新定义世界坐标系，但 map_id 不变。如果把前后两个坐标系的位姿放进同一段对齐，ATE 会严重失真。例如 easy 序列的 RGB-D+IMU，在 t≈3.2 s 做 IMU 初始化时，世界系整体旋转了约 105°。

**什么时候加 1。** 每个 OK 帧都和上一个 OK 帧比较，只读状态，不改 SLAM 行为：

- **map_id 加 1**：
  1. 跟踪进入未初始化状态（state 0/1）之后，重新回到 OK；
  2. RGB-D 的“无声重初始化”：LOST 之后，ORB-SLAM3 在同一帧内重置或新建地图，下一帧一帧就初始化成功，状态只表现为 4→2。判断方法是：上一 OK 帧所在地图的关键帧，在当前地图中一个都不剩。
- **frame_epoch 加 1**：
  - IMU 初始化、VIBA1、VIBA2；
  - 回环或全局 BA（`Map::GetLastBigChangeIdx` 增大）；
  - 地图合并；
  - 最近 20 个关键帧整体发生相似变换：旋转超过 1°、尺度变化超过 3%，或中位位移超过 0.2 m。

**验收**（早期验证结果（未随本分支提交），共 11 个运行：早期验证的 8 个配置，加 C_smoke 的 3 条 hard RGB-D）：

- 在每个段内，比较相邻帧的相对位姿与 GT 的相对位姿，阈值为旋转 10°、平移 1.0 m。
- 6 个运行的段内没有跳变。
- 其余运行共标记 18 处，再用“分段前后分别对齐”逐一复核：
  - 2 处像是漏检的世界系变化，都是缓慢渐变，单帧变化量低于阈值，影响 2 个段；
  - 3 处是局部跟踪误差；
  - 13 处所在的段太短，无法判断。
- 来源：早期验证结果（未随本分支提交） 和 `step_split_test.jsonl`。

## 7. 并发对结果的影响

数据来源：`results/A/T1b_concurrency/summary.csv`。测试在 easy 序列上进行，RGB-D+IMU 和 RGB+IMU 两种模式，IMU 种子为 0。

| 同时运行数 | 每帧耗时均值，RGB-D+IMU / RGB+IMU（ms） | 每帧超过 100 ms 的比例，RGB-D+IMU / RGB+IMU | RGB+IMU 覆盖率均值 |
|---|---|---|---|
| 1（单独，各 3 次） | 26 / 21 | 1.7% / 0.6% | 0.890 |
| 2 | 24 / 21 | 0.2% / 0.3% | 0.891 |
| 4 | 35 / 31 | 0.6% / 0.4% | 0.966 |
| 6 | 59 / 67 | 4.3% / 17.4% | 0.634 |
| 16 | 166 / 190 | 93.2% / 85.2% | 0.638 |
| 32 | 348 / 380 | 99.1% / 99.7% | 0.621 |

结论：

- 正式实验全队同时最多跑 **4 个** ORB-SLAM3。超过这个数后，跟踪处理不过来，RGB+IMU 的覆盖率明显下降。
- 即使单独运行，同一配置的在线 ATE 也很离散。例如 RGB-D+IMU 单独跑 3 次，ATE 在 0.55–6.72 m 之间。原因是当时只按 map_id 分段，同一段里混入了 IMU 初始化和回环造成的世界系变化，与并发无关。这正是引入 frame_epoch 的原因。
- ORB-SLAM3 是多线程程序，运行结果不能完全复现，所以每个配置重复跑 3 个种子。

## 8. hard 序列上 IMU 模式反复重置（实验发现）

**现象。** 数据来源：`results/A/T1_runs/office_hard_p004__IMU_RGBD__s0`。

- hard 上 RGB-D+IMU 共有 151 个跟踪段，每段 OK 帧数中位数为 3，最长 13 帧。
- 日志中 151 次 `Fail to track local map!` 后面都紧跟一次 `Reseting active map`。
- IMU 初始化一次都没有尝试过。
- RGB+IMU 情况相同：86 段，每段最长 13 帧。

**根因（ORB-SLAM3 源码）：**

1. IMU 初始化完成之前，只要跟踪失败一次，就立即调用 `ResetActiveMap()`，不尝试重定位（`src/Tracking.cc:2147–2151`）。
2. IMU 初始化至少需要 10 个关键帧（`src/LocalMapping.cc:1183/1192`），RGB-D 下还要求至少 1 s。
3. hard 序列运动太剧烈，每段跟踪撑不到这个门槛，于是陷入“建图 → 失跟 → 重置”的循环。

**运动强度。** 数据来源：GT 轨迹 `trajectory_gt.tum`。

| | easy | hard |
|---|---|---|
| 角速度 p50 / p90 / 最大（°/s） | 26 / 53 / 87 | 74 / 136 / 150 |
| 线速度 p50 / p90 / 最大（m/s） | 1.72 / 3.68 / 4.99 | 2.59 / 5.25 / 9.76 |
| 最平缓的 5 s 窗口内平均角速度（°/s） | 21 | 61 |

- hard 上，RGB-D+IMU 失跟那一帧的帧间旋转中位数为 10.5°；在 easy 上，正常跟踪时帧间旋转中位数只有 2.6°。
- 对照：在 RGB-D+IMU 失跟的那些时刻，纯 RGB-D 有 62 次仍处于 OK，82 次处于 RECENTLY_LOST。纯 RGB-D 会进入重定位，而不是直接重置。

**排除的原因与处理方式：**

- 用无噪声 IMU 重跑，现象相同，排除 IMU 噪声的影响。
- 与标定和并发无关。
- 这是 ORB-SLAM3 规则加上数据运动强度共同造成的结构性问题，按实验发现如实报告，**不调参去规避**。

## 10. 主要发现（截至目前，均来自已完成的运行）

1. **并发上限为 4。** 超过后跟踪处理不过来，覆盖率下降（见第 7 节）。
2. **在线 ATE 必须分段，并同时报告段数。** 如果不分段，IMU 初始化、回环和 RGB-D 的无声重初始化都会让 ATE 失真（见第 6 节）。
3. **hard 序列上 IMU 模式无法完成 IMU 初始化**，原因是结构性的（见第 8 节）。因此在 hard 上，“加 IMU”不仅没有帮助，覆盖率反而低于纯视觉。在 T1 的单次运行中，hard 序列各模式的覆盖率为：RGB 0.37，RGB+IMU 0.29，RGB-D 0.43，RGB-D+IMU 0.63（来源：B/C 组的早期验证运行）。正式数字以基线表为准。

## 11. 局限

- **数据范围有限**：只有一个场景、两条轨迹（easy 和 hard 各一条），而且是仿真数据。
- **结果不能逐次复现**：多线程导致每次运行结果都不同，所以只报告 3 个种子的均值和范围，不报告单次数值。
- **frame_epoch 有漏检**：缓慢渐变的世界系变化可能检测不到，验收中发现 2 处。另一方面，单目尺度漂移会被切成很多短段，使 ATE 偏乐观，所以必须结合段数来看。
- **最终轨迹不完整**：只覆盖最大的一张地图；hard 上的 IMU 模式经常连最终轨迹都没有。
- **实时性依赖负载**：实时回放下的结果受机器负载影响，正式实验已固定为全队同时最多 4 个运行。
